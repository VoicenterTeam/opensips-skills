# Milestone 1: Schema mirroring and validation

## Goal

Mirror the Zod schemas from the upstream extraction project into `scripts/schemas/`, set up the schema hash drift check, and implement the validation stage of the pipeline. At the end of this milestone, `npm run validate` runs against the source JSON tree and produces either a clean success or a structured list of validation errors with file paths and JSON paths to the offending fields.

This is the first milestone that produces working code. It is also the first milestone that touches the upstream extraction project's output, so it locks in the contract between the two projects.

## Why this is sequenced here

Validation is the entry point of the pipeline. Every later stage assumes its input is structurally valid; if validation is wrong, every downstream artifact is built on bad data. Schema validation is also the simplest part of the pipeline to implement and test in isolation — it's pure data-in, errors-out, no rendering, no filesystem writes beyond reading source files. Getting this right first means later milestones can focus on rendering logic without worrying about whether their inputs are well-formed.

The schema hash drift check is part of this milestone (not a later one) because it's the safety mechanism that makes the mirroring contract enforceable. Without it, a future schema change in the extraction project could silently produce broken output here. Wiring the check up at the same time as the schemas means the two never exist independently.

## Tasks

### Task 1.1: Add Zod and core dependencies

Update `package.json` `dependencies` and `devDependencies`:

```json
{

  },
  "devDependencies": {
    "@tsconfig/node20": "^20.x",

    "typescript": "^5.x",
    "vitest": "^2.x",
    "prettier": "^3.x",
    "eslint": "^9.x",
    "@typescript-eslint/eslint-plugin": "^8.x",
    "@typescript-eslint/parser": "^8.x",
    "eslint-plugin-jsdoc": "^50.x"
  }
}
```

Pin to specific versions in `package-lock.json` via `npm install`. Use `npm ci` in CI, never `npm install`, to keep the lockfile authoritative.

Acceptance: `npm install` produces a `package-lock.json`. `npx tsc --noEmit` still passes.

### Task 1.2: Mirror the Zod schemas

Copy the schema files from the upstream extraction project's `src/schemas/` directory into `scripts/schemas/`. The exact file list comes from the extraction project; expect roughly:

- `base.ts` — the `BaseDocument` interface and `DocType` enum.
- `module.ts` — `ModuleDocumentSchema` and the eight section sub-schemas.
- `core-variables.ts`, `core-functions.ts`, `core-parameters.ts`, `operators.ts`, `statements.ts`, `routes.ts`, `flags.ts`, `transformations.ts`, `async.ts`, `mi-commands.ts`, `events.ts`, `statistics.ts`, `guides.ts` — one file per core document type.
- `consolidated.ts` — the `ConsolidatedDocumentSchema` for the index this project will produce.
- `collection-state.ts` — the upstream extraction's progress-tracking schema (mirrored for completeness even though this project doesn't consume it directly).

Each schema is a verbatim copy. Do not modify schemas during mirroring — that defeats the point of mirroring. If a schema needs to change, the change goes upstream first, then gets re-mirrored.

Add a comment header at the top of each mirrored file:

```typescript
/**
 * Mirrored from opensips-docs-collector/src/schemas/{filename}.ts
 *
 * DO NOT EDIT THIS FILE. Schema changes flow downstream from the extraction
 * project. To update: change upstream, re-run the mirroring procedure, and
 * regenerate the schema hash via `npm run schemas:hash`.
 *
 * Schema rationale: see docs/architecture/adr/004-node-typescript-build-stack.md
 * and docs/architecture/data-pipeline.md §5.3.
 */
```

Acceptance: All schemas in `scripts/schemas/` parse via `npx tsc --noEmit` without errors. Importing any schema in a test file resolves correctly.

### Task 1.3: Implement the schema hash check

Create `scripts/schemas/hash.ts` that exports:

- `computeSchemaHash()` — reads every `.ts` file in `scripts/schemas/` (excluding `hash.ts` itself and `.schema-hash`), concatenates their contents in alphabetical order by filename, and returns the SHA-256 hex digest.
- `readCommittedHash()` — reads `scripts/schemas/.schema-hash` and returns its contents trimmed.
- `verifySchemaHash()` — calls both, returns `{ ok: boolean, computed: string, committed: string | null }`.

Add an `npm` script `schemas:hash` that runs `computeSchemaHash()` and writes the result to `scripts/schemas/.schema-hash`. This is the regeneration command for maintainers who have intentionally updated the schemas.

Add `.schema-hash` to the initial repo (with whatever the current schema set hashes to). This is the "current expected" value that CI will check against on every build.

Acceptance: `npm run schemas:hash` produces a stable hash on repeated runs (deterministic). Modifying any schema file and re-running produces a different hash.

### Task 1.4: Implement the discover stage

Create `scripts/lib/discover.ts` exporting:

- `discoverVersions(sourceRoot: string): string[]` — scans `sourceRoot/`, returns subdirectory names matching `^\d+\.\d+$`, sorted alphabetically.
- `discoverSourceFiles(sourceRoot: string, version: string): { core: string[], modules: string[] }` — for one version, lists JSON files in `core/` and `modules/`. File lists are sorted alphabetically.

Both functions throw structured errors if the source root doesn't exist or has unreadable subdirectories. Errors include the path that caused the failure.

Acceptance: Unit tests against an in-memory filesystem (`memfs`) verify version discovery handles missing directories, mixed valid/invalid subdirectory names, and empty directories.

### Task 1.5: Implement the validation stage

Create `scripts/lib/validate.ts` exporting:

- `validateSourceFile(filePath: string, schema: z.ZodType): ValidationResult` — reads the file, parses JSON, validates against the schema, returns either `{ ok: true, document }` or `{ ok: false, errors: ValidationError[] }`.
- `validateVersion(sourceRoot: string, version: string): VersionValidationResult` — orchestrates: looks up files via `discoverSourceFiles`, dispatches each to the right schema based on filename, accumulates results.
- `selectSchemaForFile(category: 'core' | 'modules', filename: string): z.ZodType` — the lookup table that maps `core/variables.json` → `CoreVariableDocumentSchema`, `modules/tm.json` → `ModuleDocumentSchema`, etc.

Use `zod-validation-error` to format Zod issues into single-line messages of the form `{json-path}: expected {type}, got {type}`.

Errors aggregate across all files in a version (fail-slow within the validation stage, per ADR data-pipeline §4). The function returns the full error list, not just the first error.

Acceptance: Unit tests cover (a) a valid module JSON producing `ok: true`, (b) a JSON parse error producing one validation error, (c) a Zod validation failure producing one or more errors with correct field paths, (d) multiple bad files in one version producing one error per bad file, (e) a missing file producing an error.

### Task 1.6: Wire up the `validate` npm script

Create `scripts/build-references.ts` as a stub orchestrator. For this milestone, it only implements the validation path:

```typescript
async function main() {
  const sourceRoot = "./source";
  const versions = discoverVersions(sourceRoot);
  let hadErrors = false;

  for (const version of versions) {
    const result = await validateVersion(sourceRoot, version);
    if (!result.ok) {
      hadErrors = true;
      printErrors(result.errors);
    } else {
      console.log(`${version}: OK (${result.fileCount} files)`);
    }
  }

  process.exit(hadErrors ? 3 : 0);
}
```

Wire `npm run validate` to call this entry point with a `--validate-only` flag that short-circuits before reaching any rendering logic (which doesn't exist yet — this is just laying the groundwork for milestone 2's CLI).

Add the schema hash check at the start of `main()`. If the committed hash differs from the computed hash, exit immediately with code 5 and a message pointing at the regeneration command:

```
ERROR: schema hash mismatch.
The schemas in scripts/schemas/ have been modified, but the committed hash
in scripts/schemas/.schema-hash has not been updated.

If this change is intentional, run:
  npm run schemas:hash
and commit the updated .schema-hash file alongside your schema changes.

Expected: {committed}
Computed: {actual}
```

Acceptance: Running `npm run validate` with no source files produces exit code 0 and no errors. Adding a malformed JSON file under `source/3.6/modules/` produces exit code 3 and a structured error naming the file. Modifying a schema without updating the hash produces exit code 5.

### Task 1.7: Add a small set of fixtures for testing

Create `tests/__fixtures__/source/3.6/`:

- `core/variables.json` — a valid `CoreVariableDocument` with two or three sample variables.
- `modules/sample-module.json` — a valid `ModuleDocument` with minimal sections populated.
- `core/variables-invalid.json` — same shape as variables.json but with one field that fails schema validation (e.g., `readable: "yes"` where boolean is expected).
- `modules/sample-module-malformed.json` — invalid JSON (truncated).

These fixtures drive the unit tests in tasks 1.4 and 1.5. They also become the basis for end-to-end tests in milestone 9.

Acceptance: All four fixtures parse correctly into the test scenarios they're intended for.

### Task 1.8: Run validation against real source

Copy a small slice of real extraction output into `source/3.6/` — say, three to five module files and one or two core files. This is preliminary; the full source set arrives in milestone 6. The point of this task is to verify validation works against real upstream data, not just synthetic fixtures.

Run `npm run validate`. Expect it to either pass cleanly (good — the schemas are mirrored correctly) or fail with errors that point at real schema mismatches (in which case the mirroring needs revisiting).

If validation fails on real data, debug by comparing the failing JSON's actual shape against the schema's expected shape. The error should be either (a) a schema bug to fix in the upstream extraction project, or (b) a mirroring drift to fix here. Resolve before moving on.

Acceptance: `npm run validate` produces exit code 0 against the small real-data slice committed to `source/3.6/`. Any errors found during this task are resolved before moving to milestone 2.

## Acceptance criteria

The milestone is done when all of the following are true:

- All Zod schemas are mirrored from the upstream extraction project into `scripts/schemas/` with the "do not edit" header on each file.
- `scripts/schemas/.schema-hash` is committed and matches the current schemas.
- `npm run schemas:hash` regenerates the hash deterministically.
- The discover and validation stages are implemented in `scripts/lib/`.
- `scripts/build-references.ts` runs the validation path end-to-end.
- `npm run validate` exits 0 against valid source, exit 3 against invalid source, exit 5 against schema drift.
- Validation errors are formatted as `{file}:{json-path}: expected X, got Y` and aggregate across files within a version.
- Unit tests for discover and validation pass via `npm test`.
- A small slice of real upstream data is committed in `source/3.6/` and passes validation.

When all of these are true, milestone 1 is complete and milestone 2 can begin.

## Risks and watch-outs

**Schema drift discovered during mirroring.** When you mirror the schemas, you may find that the upstream extraction project has shipped schema changes since the schemas were originally specified in the requirements work. This is fine — but the mirroring step is a verbatim copy, not a "fix while you're at it." If upstream has drifted, mirror what's there now and document the version in the comment header. Treating mirroring as an opportunity to "improve" schemas defeats the contract.

**Fixture maintenance burden.** It's tempting to write extensive fixtures covering every conceivable schema variant. Don't. The fixtures in this milestone exist to test the validation infrastructure, not to substitute for real data. Keep them minimal; let real source files in milestone 8 do the heavy lifting.

**Hash regeneration discipline.** The schema hash check only works if maintainers actually run `npm run schemas:hash` after schema changes. CI catches the failure case (build fails when hash drifts), but contributors will hit this as a paper cut on every legitimate schema update. Document the regeneration step prominently in the schema files' comment header — that's where someone editing a schema will look first.

**`zod-validation-error` formatting choices.** The library has multiple formatting modes. Pick one and stick with it (recommend `fromError(zodError).toString()` for the most actionable output). If you switch later, every error message in every test fixture changes, which is painful.

**Real source data may surface upstream bugs.** Task 1.8 is the first time real extraction output flows through validation. If validation finds real bugs in upstream data, those need fixing upstream before this milestone can complete. Don't paper over real bugs by relaxing the schema here — that breaks the entire pipeline's correctness guarantee.

**ESM and TypeScript path resolution.** Node ESM with TypeScript has historically had import-resolution issues (file extensions in imports, etc.). Get the TypeScript→ESM toolchain working cleanly here. Issues debugged once at this stage save weeks of friction across later milestones.

## Parallelization notes

Task 1.1 (dependencies) and Task 1.2 (schema mirroring) are nearly independent and can be done in either order. Task 1.3 (hash check) depends on 1.2. Task 1.4 (discover) is independent of 1.2 and 1.3 — it doesn't touch schemas at all. Task 1.5 (validation) depends on 1.2, 1.3, and 1.4. Tasks 1.6 (CLI wiring) and 1.7 (fixtures) depend on 1.5. Task 1.8 (real-data validation) is the closing action.

For solo work, do them in order. For two-person work, one person can handle 1.1–1.3 (the schema work) while the other handles 1.4 (discover) in parallel; they meet at 1.5.
