# Skill Authoring Guide

> **Purpose:** Defines how the three hand-authored `SKILL.md` files in this project are written, structured, and maintained. These are the only Markdown files in the plugin's skills directory that are not generated by the build pipeline. They carry the anti-hallucination load.
>
> **Audience:** Anyone modifying `opensips-routing/SKILL.md`, `opensips-modules/SKILL.md`, or `opensips-security-advisor/SKILL.md`. Read this entire document before editing any of those files.
>
> **Status:** Authoritative. Changes require an ADR.

---

## 1. What this guide is for

The plugin's three skills coordinate via shared structural conventions, but each `SKILL.md` is hand-authored prose, not generated content. A change to a `SKILL.md` cannot be regenerated from a JSON source — it can only be reviewed against this guide and tested against the golden-path demos.

This matters because `SKILL.md` files are the most consequential text in the project. Every Claude Code session that triggers one of these skills loads its frontmatter unconditionally and may load its body. The frontmatter description is what Claude reads to decide whether to activate at all. The body is what Claude follows when it does activate. Mistakes in either compound across thousands of user sessions.

The guide covers four areas, in roughly the order an author works through them:

1. **Description writing** — getting the YAML frontmatter right so the right skill triggers for the right prompts.
2. **Multi-skill coordination** — making sure the three skills don't compete for prompts, redundantly trigger, or contradict each other.
3. **Anti-hallucination guardrails** — the patterns that prevent Claude from importing identifiers from sibling projects in the SIP Express Router lineage, or from constructing identifiers from training-data priors when its training data is stale.
4. **Body structure and length** — the canonical layout for the body of a `SKILL.md`, with concrete templates for each of the three skills.

If you are writing a new `SKILL.md` from scratch, work through the sections in order. If you are modifying an existing one, jump to the relevant section but do not skip §3 — the anti-hallucination guardrails are the project's reason for existing and any change to a `SKILL.md` body must preserve them.

## 2. Description writing

The description in YAML frontmatter is the only text Anthropic's runtime reads when deciding whether your skill is relevant to a user prompt. It is loaded into the system prompt at session start and competes with every other installed skill's description for Claude's attention. Write it as if Claude has never heard of OpenSIPs and has to decide, in one read, whether this skill is relevant.

### 2.1 The four-part structure

Every description in this project follows the same four-part shape, derived from observation of production Anthropic skills:

1. **Capability summary** — one sentence, third-person, present tense, naming what the skill does.
2. **Trigger enumeration** — concrete keywords, file types, and contexts that should activate the skill.
3. **The "use whenever" or "use even if" clause** — a phrase that explicitly loosens activation beyond literal keyword matching.
4. **The exclusion clause** — what the skill must not be used for, especially identifiers or domains it could be confused with.

Production examples of this shape from Anthropic's own skills include `pdf`, `docx`, `pptx`, and `xlsx`. The pattern works because each part addresses a distinct failure mode: capability summary anchors meaning, trigger enumeration covers literal keyword matches, the "whenever" clause covers paraphrased prompts, and the exclusion clause prevents misfiring on adjacent domains.

### 2.2 Front-load the discriminator

Claude Code displays descriptions in a per-session listing, and the listing is truncated at approximately 250 characters per skill before it reaches the model's selection logic. The combined `description` plus optional `when_to_use` budget per skill is approximately 1,536 characters in some surfaces, with an aggregate budget around 16,000 characters across all installed skills. These limits change between Claude Code releases.

The practical rule: **the most distinctive content must appear in the first 250 characters of the description**. For this project, "distinctive" means two things — naming OpenSIPs explicitly, and explicitly excluding the sibling SIP Express Router lineage. If those two facts are present in the first sentence, the skill remains identifiable even when the rest of the description is truncated.

A description that hides the OpenSIPs/sibling-project distinction in the third sentence will misfire on Kamailio prompts whenever Claude Code's truncation reaches the second sentence and stops.

### 2.3 Length

The hard limit is 1024 characters. The empirical sweet spot, based on Anthropic's own production skills, is roughly 400 to 800 characters of essential content, with the remainder used for additional triggers and exclusions that may or may not survive truncation.

Descriptions tend to grow during iteration. Resist this. A description that lists every conceivable trigger keyword becomes incoherent and competes with itself for Claude's attention. Better to enumerate the half-dozen most likely user phrasings and trust the "use whenever" clause to handle the rest.

### 2.4 Voice

Always third person. Always present tense. Anthropic's documentation is explicit that first-person ("I can help you...") and second-person ("You can use this to...") cause discoverability problems because the description is injected into the system prompt and inconsistent point-of-view confuses the model's reasoning about what is being described.

Use imperative verbs for the action ("Authors and edits...", "Provides authoritative reference data...", "Reviews configurations for security issues..."). Avoid hedging verbs ("Helps with...", "Can be used for..."). The capability summary states what the skill does, not what it can do.

### 2.5 Trigger keywords

Include both natural-language phrases and technical terminology. A SIP engineer might type "write me a route for incoming INVITEs" or might type "request_route handling for INVITE method" — the description should accommodate both. Concrete identifiers (function names, parameter names, pseudo-variables, route block types) belong in the trigger list because Claude pattern-matches against them.

Avoid generic verbs that match every prompt ("create", "make", "do"). They inflate the description without improving triggering.

### 2.6 The exclusion clause

For this project, every description includes an exclusion against the SIP Express Router lineage, naming the sibling projects (Kamailio, OpenSER, SER) explicitly. The exclusion appears in the first 250 characters because of truncation considerations.

Production exclusion phrasings that work:

- "Do NOT use for [sibling] configurations — those use different identifiers despite shared lineage."
- "SKIP: prompts mentioning [sibling] modules or [sibling] syntax."
- "Not applicable to [sibling] — see that project's own tooling."

Avoid soft exclusions ("primarily for OpenSIPs") which Claude treats as preferences rather than constraints.

### 2.7 The three project descriptions

The current descriptions for the three skills, with annotations:

**`opensips-routing`:**

> Authors and edits OpenSIPs SIP server configuration scripts (`opensips.cfg`, route blocks, modules, parameters). Use whenever the user mentions OpenSIPs, opensips.cfg, route{}/branch_route/failure_route, $var/$avp/$pv pseudo-variables, or asks to write/edit SIP routing logic for OpenSIPs. Do NOT use for Kamailio, OpenSER, or SIP Express Router (SER) configurations — those use different identifiers despite shared lineage.

This description front-loads OpenSIPs in the first word, names concrete trigger identifiers (`route{}`, `branch_route`, `failure_route`, `$var`, `$avp`, `$pv`), uses the "use whenever" clause, and ends with a hard exclusion naming all three sibling projects within the first ~400 characters.

**`opensips-modules`:**

> Provides authoritative per-module reference data for OpenSIPs modules (function signatures, exported parameters, dependencies). Use whenever the user references a specific OpenSIPs module by name (e.g. dialog, tm, rr, registrar, dispatcher, drouting, presence, sl, uac, db_mysql, mid_registrar) or asks what functions/parameters a module exports. Do NOT use for Kamailio modules even if they share a name.

The capability summary frames this skill as a reference rather than an authoring tool, distinguishing it from `opensips-routing`. The exclusion specifically addresses the most likely confusion ("Kamailio modules even if they share a name") because module name overlap is the highest-risk identifier confusion in the SER lineage.

**`opensips-security-advisor`:**

> Reviews OpenSIPs configurations for security issues (SIP authentication, ACL/firewall rules, rate limiting, INVITE flooding, registration hijacking, RTP relay exposure). Use whenever the user asks for a security review, audit, or hardening check on an OpenSIPs config, or mentions specific risks like 'SIP scanning', 'spoofed REGISTER', or 'toll fraud' in an OpenSIPs context. Do NOT use for general SIP security advice unrelated to OpenSIPs configuration.

This description names the security domain ("SIP authentication", "INVITE flooding", "toll fraud") so the skill triggers on security-flavored prompts, but explicitly scopes itself to OpenSIPs configuration to avoid pulling in every general SIP security question.

### 2.8 Iterating on descriptions

Description quality is empirically validated, not theoretically reasoned. The validation method:

1. Build a test set of approximately 20 prompts: 8–10 that should trigger the skill, 8–10 "near-miss" prompts that share vocabulary but should not trigger (Kamailio prompts, generic SIP prompts, unrelated network tasks).
2. Run each prompt through Claude Code with all three skills installed.
3. Measure activation rate on the should-trigger set and false-fire rate on the should-not-trigger set.
4. Iterate the description, focusing on whichever metric is worse.

The should-not-trigger set is the more diagnostic of the two. A description that activates on 90% of OpenSIPs prompts but also activates on 40% of Kamailio prompts is worse than one that activates on 80% of OpenSIPs prompts and 5% of Kamailio prompts. False positives in this domain mean Claude confidently writes Kamailio syntax into an OpenSIPs config and the user discovers the problem in production.

## 3. Multi-skill coordination

The three skills coordinate through written conventions, not formal mechanisms. There is no "skill A depends on skill B" declaration in Claude Code's runtime; coordination happens because each `SKILL.md` body and description names its siblings and tells Claude when to defer to them.

### 3.1 The hub-and-spoke pattern

`opensips-routing` is the hub. It is the skill most likely to trigger first for a user prompt about OpenSIPs, because authoring is the most common use case. Its body's role is to recognize when a prompt has crossed into territory better served by `opensips-modules` (specific module reference data) or `opensips-security-advisor` (security review), and to instruct Claude to consult those skills.

`opensips-modules` and `opensips-security-advisor` are the spokes. They focus on their narrow domains and do not attempt to handle authoring tasks themselves. Their bodies acknowledge `opensips-routing` as the authoritative source for routing logic.

This pattern lets multiple skills load in the same session without competing. A complex prompt — "review my opensips.cfg for security issues, especially around the dialog module" — can legitimately trigger all three skills, each contributing its specialty.

### 3.2 Cross-references in descriptions

Descriptions briefly name the sibling skills when relevant. Example phrasing in `opensips-routing`: *"For per-module function signatures and exported parameters, the `opensips-modules` skill is the authoritative source."* This appears in the body, not the frontmatter, because frontmatter description budget is too tight to spend on cross-references.

### 3.3 Cross-references in bodies

In each skill's body, the second paragraph (immediately after the cross-project guardrail in §4) names the sibling skills and their roles. Example for `opensips-routing`:

> When the user asks about a specific module's functions, parameters, or pseudo-variables, the `opensips-modules` skill provides authoritative per-module reference data. Consult it before answering. When the user asks for a security review, audit, or hardening check, the `opensips-security-advisor` skill provides the review workflow. The three skills are designed to be loaded together; do not attempt to duplicate their work.

This is enough context for Claude to make routing decisions during a session. It is not enough context to be a substitute for those siblings — Claude still has to read their bodies to act on their content.

### 3.4 What multi-skill coordination does not solve

Coordination prose makes the skills cooperate when they are all loaded. It does not solve the case where Claude Code fails to load one of them because its description didn't trigger. If `opensips-modules` doesn't activate on a prompt that mentions a module by name, the body of `opensips-routing` saying "consult `opensips-modules`" cannot rescue the situation — the modules skill's content is not in context.

This is why §2.8's iterative description validation is the most important step. Coordination is downstream of triggering.

### 3.5 The integration contract with the security advisor

The `opensips-security-advisor` skill is authored separately by another agent (per ADR-005). The integration contract from this project's perspective is read-only:

- The advisor may read reference files in `opensips-modules/references/` and `opensips-routing/references/`.
- The advisor may not write to either directory.
- The advisor's `SKILL.md` is owned by the security agent. This project owns the placeholder scaffold, not the populated content.

When this project's maintainers review changes to the advisor's `SKILL.md`, they verify only that the description respects the four-part structure and the exclusion convention; the body's content is the security agent's responsibility.

## 4. Anti-hallucination guardrails

The project exists because Claude reliably hallucinates OpenSIPs identifiers — usually by importing them from training data on Kamailio, OpenSER, or SER. This is a real failure mode, not a theoretical one. The guardrails in `SKILL.md` bodies are what prevent it.

### 4.1 The cross-project guardrail section

Every `SKILL.md` body in this project includes a "Cross-project guardrail" section near the top, immediately after the overview. The section follows this template:

```markdown
## Cross-project guardrail

OpenSIPs descended from the SIP Express Router (SER) and shares a code lineage with Kamailio (formerly OpenSER). The function names, module names, and pseudo-variable syntax differ between projects. Common confusions:

- Kamailio's `pv_*` function family is not OpenSIPs syntax. OpenSIPs uses `$var(name)`, `$avp(name)`, `$pv(name)` for pseudo-variable manipulation.
- Kamailio's `tmx`, `dmq`, `kazoo` modules do not exist in OpenSIPs.
- OpenSIPs has `proto_*` modules where Kamailio uses `tcpops`/`websocket`.

If you recognize an identifier from your training data but cannot find it in the `opensips-modules` reference set, assume it is from a sibling project and ask the user. Do not construct identifiers from your priors.
```

The section appears in all three skills with minor adjustments for context. The same content is correct across them because the failure mode is the same.

### 4.2 Why "ask the user" instead of "do not use"

The closing instruction is "ask the user, do not construct," not "never use Kamailio syntax." The reasoning: an instruction to "never use X" without an alternative pathway leaves Claude in an undefined state when it encounters X. An instruction to "ask the user" gives Claude a concrete next action that resolves the ambiguity.

This pattern matches how Anthropic's own `claude-api` skill handles model identifiers: "If any of the model strings above look unfamiliar to you, that's to be expected — that just means they were released after your training data cutoff." For this project, the analogous framing is: "If an identifier looks familiar but isn't in the references, it's probably from a sibling project."

### 4.3 The Bad/Good paired-example pattern

Anti-hallucination prose works better when accompanied by paired examples showing the wrong and right forms. Bare prohibitions ("don't use Kamailio syntax") leave Claude without a target; paired examples define both the boundary and the alternative.

```markdown
**Pseudo-variable access:**

- Bad (Kamailio): `pv_get_authattr(...)`
- Good (OpenSIPs): `$authattr` — see `references/{version}/core/variables.md`

**Module loading:**

- Bad (Kamailio): `loadmodule "tmx.so"`
- Good (OpenSIPs): The `tmx` module does not exist in OpenSIPs. Use `tm` and consult `references/{version}/modules/tm.md`.
```

The paired form pulls Claude toward the correct identifier rather than leaving it to construct one. Use it for any identifier confusion that has been observed in practice.

### 4.4 Force the reference detour

The strongest anti-hallucination tactic is to instruct Claude not to construct identifiers from training data, but to read the relevant reference file. This is the same pattern as `claude-api`'s "read shared/models.md for the exact ID — do not construct one yourself."

For this project, every place a `SKILL.md` body would mention a function, parameter, or pseudo-variable, the body instead points at the relevant reference path:

> When suggesting a function call, consult `references/{version}/modules/{module}.md` for the exact signature. Do not infer arguments or return types from your training data.

This forces a Read tool call, which is the deterministic act that grounds Claude in version-correct content.

### 4.5 Reserve all-caps for genuine constraints

Anthropic's `skill-creator` documentation flags all-caps imperatives ("ALWAYS", "NEVER", "MUST") as a yellow flag — they tell Claude what to do without telling it why, which leaves no rubric for unanticipated cases. The recommended default is to explain the reason and let Claude reason about edge cases.

There are exceptions where all-caps is correct: cross-project identifier leakage, security-critical commands, and machine-checked invariants. In each case the all-caps imperative is immediately followed by an explanation. Example from this project's `opensips-routing` body:

> **CRITICAL: Use only OpenSIPs identifiers.** OpenSIPs descended from the SIP Express Router lineage and shares a code base ancestry with Kamailio. The function names, module names, and pseudo-variable syntax differ between projects, despite surface similarity. Mixing identifiers across projects produces configs that look correct but fail at runtime in subtle ways.

The imperative is followed by the rationale. Claude then has both the rule and the reasoning to apply it correctly in cases the author did not anticipate.

Everywhere else, use the explain-the-why pattern: state the constraint as a sentence, then immediately state the reason. "Use constructor injection. Field injection breaks testability because we cannot mock the field without Spring context" beats "MUST use constructor injection. NEVER use field injection."

### 4.6 Negative examples without backfire

The general LLM-prompting research is mixed on negative instructions ("don't do X"). The reconciled rule across the evidence: paired examples (Bad → Good) work; bare prohibitions without alternatives can backfire by anchoring the model on the wrong pattern.

For this project, the rules are:

- Use the Bad/Good paired-example pattern (§4.3) for identifier-level confusions.
- Use named anti-pattern lists ("Common confusions") with concrete alternatives.
- Avoid bare prohibitions like "Do not write Kamailio code." They give Claude no concrete target and may even surface the prohibited pattern by anchoring on it.

### 4.7 Version-specific behavior

The plugin supports multiple OpenSIPs versions concurrently (3.5 and 3.6 at the time of writing). Version-specific behavior is handled by the same "force the reference detour" principle:

> When the user specifies an OpenSIPs version, consult `references/{version}/...` paths. Do not assume features from one version exist in another. Module function signatures, pseudo-variable availability, and parameter defaults can change between minor versions.

This is enough — it tells Claude the version-isolation rule and points at the directory structure that enforces it.

The `SKILL.md` body does not enumerate version differences or maintain a "what's new in 3.6" section. That information lives in the per-version reference files.

## 5. Body structure

This section specifies the canonical layout of each `SKILL.md` body. The structure is the same for all three skills with content variation; following the same skeleton across skills makes them easier to read together and easier to maintain.

### 5.1 Length budget

Anthropic's documented soft cap is 500 lines or 5,000 words for `SKILL.md` body. Production Anthropic skills (`pdf` at 314 lines, `docx`, `pptx`, `xlsx` all comfortably under) consistently stay well under this cap. The mechanical reason: once a skill is loaded, its body persists in context for the entire session, and large bodies risk being dropped during auto-compaction.

This project targets approximately 250 to 400 lines per `SKILL.md` body. Content beyond that goes into reference files, which Claude loads on demand.

### 5.2 Section order

Every `SKILL.md` body in this project has the following sections, in this order:

1. **`## Overview`** — one to three sentences naming what the skill does and how it relates to the other two.
2. **`## Cross-project guardrail`** — the section described in §4.1.
3. **`## When to use this skill`** — when the skill is the right one to consult versus deferring to a sibling.
4. **`## Decision table or workflow`** — varies by skill (see §5.4–§5.6).
5. **`## Common tasks`** or **`## Module index`** or **`## Workflow checklist`** — the substantive content, varies by skill.
6. **`## References`** — pointers to reference files this skill uses.
7. **`## Working with sibling skills`** — coordination notes.

Sections 1, 2, and 3 are nearly identical across the three skills. Sections 4–6 are skill-specific. Section 7 is brief and consistent.

### 5.3 The opening (sections 1–3)

The first 80 to 100 lines of every `SKILL.md` are nearly identical in structure. This is intentional — the opening is what Claude reads first, and consistent structure across the three skills means Claude encounters the same anchoring concepts (what skill, sibling lineage warning, when to use) in the same order regardless of which one triggered.

Template:

```markdown
## Overview

This skill {does X}. It is one of three coordinated skills for working with OpenSIPs in Claude Code; see "Working with sibling skills" below for how it relates to `opensips-routing`, `opensips-modules`, and `opensips-security-advisor`.

## Cross-project guardrail

{The full text from §4.1, with module-confusion examples appropriate to this skill's domain.}

## When to use this skill

This skill should be the active one when:
- {Concrete trigger 1}
- {Concrete trigger 2}
- {Concrete trigger 3}

This skill should defer to `{sibling skill}` when:
- {Concrete handoff condition 1}
- {Concrete handoff condition 2}
```

The "When to use" section is more granular than the description in frontmatter. The frontmatter description triggers activation; the body's "When to use" section guides Claude's behavior once activated.

### 5.5 `opensips-modules` body (sections 4–6)

The modules skill is a router-index per ADR-001. Its body is shorter than `opensips-routing` because the substantive content lives in the per-module reference files, not the SKILL.md.

```markdown
## How to use this skill

When the user names an OpenSIPs module, read `references/{version}/modules/{module-slug}.md` for that module's reference data. Do not infer function signatures, parameter names, or pseudo-variables from your training data — the per-module reference files are the authoritative source.

If the user names a module not in the index below, it may be a Kamailio module or a typo. Confirm with the user before proceeding.

## Module index

| Module | Purpose | Reference file |
|---|---|---|
| `tm` | Stateful SIP transactions | references/{version}/modules/tm.md |
| `dialog` | Dialog tracking and timeout management | references/{version}/modules/dialog.md |
| `dispatcher` | Load-balancing across destinations | references/{version}/modules/dispatcher.md |
| ... | ... | ... |

(The index is generated from consolidated.json at build time. Do not hand-edit.)

## When a module is not in the index

If the user mentions a module name that does not appear in the index above:
1. Check for typos (a leading `mid_` vs. `mid-`).
2. Ask the user whether they're sure the module is part of OpenSIPs — common Kamailio module names that do not exist in OpenSIPs include `tmx`, `dmq`, `kazoo`.
3. Do not invent module data based on training-data priors.

## References

The per-module reference files in `references/{version}/modules/` are the authoritative source.
```

The module index table is generated at build time from `consolidated.json` and pasted into the body. Hand-editing it is forbidden — Rule 1 in `CLAUDE.md` applies.

### 5.7 Section 7: working with sibling skills

This section is brief and nearly identical across the three:

```markdown
## Working with sibling skills

This skill is one of three coordinated skills:
- `opensips-routing` — authoring SIP routing logic for OpenSIPs.
- `opensips-modules` — authoritative per-module reference data.
```

The section's purpose is to give Claude a quick refresher on the cooperative architecture if it has loaded only this one skill and is uncertain whether to handle a tangential question.

## 6. Reference-file linking conventions

Reference files are loaded by Claude on demand when the body's prose names them. The conventions for naming them are:

### 6.1 One hop

Every reference file is one level deep from the `SKILL.md` body. The body says "see `references/{version}/modules/tm.md`" and Claude reads that file directly. Nested references — where `tm.md` says "see `references/{version}/modules/tm/timers.md`" — cause Claude to use partial reads (`head -100`) and miss content. Production Anthropic skills consistently keep references one hop.

### 6.2 Imperative phrasing

Reference-file pointers are imperative: "Read `references/{version}/core/variables.md` for the exhaustive list," not "More information is available in `references/{version}/core/variables.md`." Imperative voice triggers Claude's read action; passive voice gets skimmed.

Production examples from Anthropic's `pdf` skill: *"Read FORMS.md and follow its instructions."* This phrasing is the model.

### 6.3 The version placeholder

Reference paths in the body use `{version}` as a placeholder. Claude substitutes it at read time based on the resolved active version. The build script does not pre-substitute — the body files are version-agnostic; only the reference tree is version-scoped.

### 6.4 No Markdown links across files

Within a single file, anchor links (`[Section](#section)`) work. Across files, use prose with bare paths: "see `references/{version}/modules/tm.md` and search for the `t_relay` heading." This matches production Claude skill conventions and is more robust to file renames.

## 7. Maintenance discipline

This section documents the operational rules for changing `SKILL.md` files.

### 7.1 The change must be tested

Every change to a `SKILL.md` is tested against the golden-path demos before merge. The demos are the regression test for skill behavior — if a change to a description, body section, or reference pointer regresses any demo, the change is reverted, not patched.

The golden-path demos exercise activation (does the skill trigger for the expected prompts?) and behavior (does the skill produce correct output once activated?). Both must pass.

### 7.2 The change must preserve the cross-project guardrail

The cross-project guardrail (§4.1) is the project's reason for existing. A change that weakens or removes it is a release blocker. Reviewers verify the guardrail is present and substantively unchanged on every PR that touches a `SKILL.md`.

### 7.3 The change must justify length increases

`SKILL.md` bodies have a target length around 250–400 lines. A change that pushes a body past 500 lines requires a rationale in the PR description and a discussion of whether the new content belongs in a reference file instead.

### 7.4 Description changes require iteration evidence

A change to a frontmatter description requires evidence that the change improves activation behavior. The minimum is the validation procedure in §2.8: run the change against the test set of approximately 20 prompts and confirm activation rate and false-fire rate are at least as good as before.

A description change merged without iteration evidence is a regression risk because trigger behavior is not statically verifiable.

### 7.5 The three descriptions evolve together

Because the three skills share a domain, a change to one skill's description often implies a change to another's. If `opensips-routing`'s description is broadened to include a new trigger, check whether the broadened wording overlaps with `opensips-modules` or `opensips-security-advisor`. Coordinated changes go in one PR; sequential changes cause description drift.

This guide is not a tutorial on Claude Code Agent Skills. The reader is assumed familiar with the Agent Skills architecture (frontmatter loading, body activation, progressive disclosure). External references for the architecture itself: Anthropic's official Agent Skills documentation and the `anthropics/skills` repository.

This guide is not a style guide for the reference files. Reference file structure is specified in `docs/architecture/rendering-templates.md`. The two documents address different audiences — this guide addresses authors of the three hand-authored `SKILL.md` files; the rendering templates document addresses developers of the build pipeline that produces the generated reference files.

This guide is not a specification of the runtime behavior. How Claude Code loads skills, when frontmatter is read, when bodies are loaded, and how the Read tool resolves paths are runtime concerns documented elsewhere. This guide assumes the documented behavior and explains how to write content that takes advantage of it.
