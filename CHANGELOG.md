## [Unreleased]

### Fixed
- **Rendering-time sanitization for upstream extraction artifacts.** Generated reference files no longer carry three classes of upstream `opensips-docs-collector` damage: `U+FFFD` replacement characters in DocBook-derived section anchors (487 occurrences), over-escaped `\_` underscores in identifiers (~14k occurrences), and `U+200B` zero-width spaces (4 occurrences). A new pure helper (`scripts/lib/sanitize.ts`) is wired into `renderModule`, `renderCoreDocument`, `renderGuide`, the `consolidated.json` description path (`build-consolidated/index.ts#firstSentence`), and the `SKILL.md` module-index `Purpose` column (`build-module-index/index.ts#extractPurpose`), so every place a description leaves the source JSON gets the same cleanup. The committed source under `data/` is untouched — only the *rendered* output is cleaned, preserving the upstream-resync workflow. Per ADR-010, this is a deliberate, narrow exception to CLAUDE.md Rule 3 with three explicit criteria gating any future additions to the rule set; the upstream fix in `opensips-docs-collector` will retire this layer. 12 new unit tests in `tests/unit/lib/sanitize.test.ts`; golden fixtures regenerated.
- **Cross-platform schema-hash stability.** `computeSchemaHash` in `scripts/schemas/hash.ts` previously hashed raw file bytes via `readFileSync(abs)`, which produced different digests on Windows checkouts (CRLF, the Git-for-Windows `core.autocrlf=true` default) versus Linux/macOS (LF) — directly contradicting the function's stated "stable across operating systems" guarantee. The fix normalises `\r\n` → `\n` before hashing so the digest depends only on canonical content. The committed baseline `scripts/schemas/.schema-hash` was simultaneously stale (M1's `006ad281…` matched neither platform's computed hash); regenerated via `npm run schemas:hash` to the canonical `35ed9745…`. A new unit test asserts identical CRLF/LF inputs produce the same hash, codifying the invariant. Per ADR-011, the two defects compounded but share a single root cause; both are now fixed. Net effect: 31 previously-failing orchestrator/e2e tests now pass; full suite at **773/773 green**.

### Documentation
- **ADR-010** — Rendering-time output sanitization for upstream extraction artifacts.
- **ADR-011** — CRLF-tolerant schema hash for cross-platform stability.

## [1.0.0] - 2026-04-25

### Added
- **M0 — Repository scaffolding.** Directory structure, GPL-3.0 license, .gitignore, package.json with placeholder scripts, tsconfig.json with strict mode, ESLint flat config with JSDoc enforcement, Prettier configuration, Claude Code plugin manifests (marketplace.json + plugin.json), and the full documentation set (CLAUDE.md, vision, requirements, architecture docs, ADRs 001-009, 11 milestone files, research reports, schema specs, testing strategy, superpower execution plan).
- **ADR-009.** `data/` adopted as the canonical source-data location (deviating from the plan's `source/`); build dynamically discovers versions from `data/{X.Y}/` folders matching `^\d+\.\d+$`; current scope expanded from {3.5, 3.6} to {3.4, 3.5, 3.6}; guides included in v1 wherever the data has them.
- **M1 — Schema mirroring and validation.** Mirrored 19 Zod schemas verbatim from upstream `opensips-docs-collector/src/schemas/` to `scripts/schemas/` with "DO NOT EDIT" headers; deterministic SHA-256 schema-hash check (`npm run schemas:hash`) protects the mirroring contract; dynamic version-discovery stage (`scripts/lib/discover.ts`) pattern-matches `^\d+\.\d+$` and detects optional `guides/` directory per ADR-009; per-file validation stage (`scripts/lib/validate.ts`) maps filenames to Zod schemas and accumulates structured `ValidationIssue`s with parse/schema/io/schema-lookup kinds; orchestrator stub (`scripts/build-references.ts`) wires `npm run validate` end-to-end with the structured exit-code taxonomy from data-pipeline.md §4 (0=success, 2=usage, 3=validation, 5=schema-drift); 51 unit tests across hash/discover/validate.
- **M2 — Core pipeline foundation.** Structured `BuildError` hierarchy with `EXIT_CODES` (`scripts/lib/errors.ts`); filesystem helpers (`atomicWriteFile`, `cleanDirectory`, `ensureDirectory`, `readJsonFile`, `posixPath` in `scripts/lib/fs-helpers.ts`); environment normalization (`normalizeEnvironment` setting `LANG=C LC_ALL=C TZ=UTC` in `scripts/lib/environment.ts`); typed `CliOptions`/`VersionResult`/`BuildSummary` (`scripts/types/cli.ts`); full Commander-based CLI (`scripts/lib/cli-parser.ts`) with all flags from data-pipeline §6.3 (`--only`, `--only-module`, `--dry-run`, `--fail-fast`, `--verbose`, `--quiet`, `--json`, `--source-root`, `--output-root`, `--validate-only`); human + JSON output modes (`scripts/lib/output.ts`); orchestrator (`scripts/build-references.ts`, 165 lines, under the 200-line budget) that delegates per-version processing to `scripts/lib/orchestrator-helpers.ts` (renderers will plug in here in M3-M5 without touching orchestration logic); `npm run build` wired end-to-end with dry-run reporting "would render N modules / N core files / 1 consolidated index" until renderers exist; `npm run clean` script. 92 new tests (36 errors + 19 fs-helpers + 10 environment + 9 cli-parser + 11 output + 7 build-references); 143 total project tests passing.
- **M3 — Per-module rendering.** Foundation libraries: `scripts/lib/markdown-builders.ts` (12 composable helpers including `renderH1-H4`, `renderSection` with empty-omission, `renderTOC`, `toAnchor`); `scripts/lib/frontmatter.ts` (canonical provenance HTML comment per rendering-templates §2.2 with newline/comment-terminator rejection); `scripts/lib/slug.ts` (filename slugifier with collision detection per data-pipeline §2.3); `scripts/lib/validate-markdown.ts` (rendered-Markdown structural validator per rendering-templates §10, fence-aware single-h1 detection, configurable thresholds, length-warn at 1200 / hard-error at 5000 with splitting deferred to a future milestone). Eight per-element renderers under `scripts/render-module/elements/` (`parameter`, `function`, `pseudo-variable`, `mi-command`, `statistic`, `event`, `config-example`, `dependencies`), each with a `headingLevel` parameter prepared for M4 reuse at H2. Module composer (`scripts/render-module/index.ts`) producing complete files in canonical section order (Overview → How It Works → Dependencies → Exported Parameters/Functions/Pseudo-Variables/MI/Statistics/Events → Configuration Examples) with dynamic TOC, alphabetical sub-element ordering, and post-pass collapse of excess blank lines. Orchestrator integration via `scripts/lib/orchestrator-helpers.ts` slug-uniqueness check and per-version atomic writes through `atomicWriteFile`. **194/194 modules render for 3.6, 137/137 for 3.5; build-twice diff is empty (deterministic).** Five validator rules relaxed from error to warning to accommodate legitimate upstream content patterns (raw HTML in descriptions, `#` markers in upstream prose treated as code, skipped heading levels in DocBook-derived content) — full rationale in `scripts/lib/validate-markdown.ts` JSDoc. 283 new tests (35 markdown-builders + 14 frontmatter + 29 slug + 150 element renderers + 17 module composer + 27 markdown validator + 4 module-rendering integration + 7 fix-ups); 426 total project tests passing.
- **M4 — Core type rendering and guides.** Five core-only element renderers (`renderOperator`, `renderStatement`, `renderRouteBlock`, `renderTransformation`, `renderFlag` under `scripts/render-core/elements/`) joining the M3-reused renderers (`parameter`, `function`, `pseudo-variable`, `mi-command`, `statistic`, `event`) at H2 via the `headingLevel` parameter; per-doc-type lead paragraphs (`scripts/render-core/lead-paragraphs.ts`, twelve hand-authored "read this file when…" triggers, plus three guide variants); aggregated core composer (`scripts/render-core/index.ts`) with a centralised `satisfies Record<CoreDocType, …>` dispatch table mapping each core doc type to its element renderer, sort key, and TOC anchor builder; guide composer (`scripts/render-guide/index.ts`) emitting type-specific section orderings for `installation_guide`, `configuration_guide`, and `syntax_guide` with the no-empty-sections rule; orchestrator integration (`scripts/lib/orchestrator-helpers.ts` extended with `renderCoreForVersion` and `renderGuidesForVersion`) writing core/guide files atomically under `opensips-routing/references/{version}/{core,guides}/` per ADR-005, with the validator running in `topLevelItemHeading: 2` mode for both, and `--dry-run` reporting separate "Would render N core files" / "Would render K guide files" lines (guides line suppressed when K=0). Markdown validator extended with the `topLevelItemHeading: 2` knob (no new relaxations needed — the M3 fix-ups carried over). **Counts: 194 modules + 12 core + 3 guides = 209 files for 3.6; 137 modules + 12 core + 0 guides = 149 files for 3.5; build-twice diff is empty (deterministic).** New tests: 4 orchestrator-core-guides integration tests (full-source, no-guides, build-twice determinism, path-placement); 662 total project tests passing.
- **M5 — Consolidated index.** Four cooperating components produce the per-version `consolidated.json` lookup aid: types + Zod schemas (`scripts/types/consolidated.ts`), pure-function builder (`scripts/build-consolidated/index.ts`), deterministic serializer (`scripts/build-consolidated/serialize.ts` via `json-stringify-deterministic`), and statistical canary (`scripts/build-consolidated/canary.ts`). The shipped index is **lightweight** — name → `{source, path, description}` lookup tables for functions, parameters, pseudo-variables, and MI commands, plus a `moduleDependencies` graph and a `statistics` block — distinct from the upstream `ConsolidatedDocumentSchema` (which embeds full document content for MCP consumption). Per ADR-006, this project ships only lookup data; full content lives in the rendered Markdown alongside. The lightweight schema lives in `scripts/types/consolidated.ts` rather than mutating the mirrored upstream schema (preserving the ADR-004 mirroring contract). Per ADR-009, the canary baseline is keyed by version (`scripts/build-consolidated/.statistics-baseline.json`'s `baselines: { "3.5": {...}, "3.6": {...} }` shape), so adding a new version is purely a data operation: `npm run baseline:update -- --only X.Y`. Orchestrator integration in `scripts/lib/orchestrator-helpers.ts#buildAndWriteConsolidatedIndex` runs after both renderers complete: build → emit collision warnings → re-validate against `ConsolidatedIndexSchema` (defence in depth) → run canary against committed baseline → serialize deterministically → atomic write to `plugins/opensips/skills/opensips-modules/references/{version}/consolidated.json` (per ADR-005, the index belongs to the modules skill). Dry-run mode emits the verbose stats line with a `(dry-run)` suffix but writes nothing; first-run on a fresh version surfaces a one-time hint pointing at `npm run baseline:update`. **3.6: 194 modules / 580 fns / 1530 params / 228 pvars / 258 MI / 47 evts / 126 stats / 3 guides → 300 KB consolidated.json. 3.5: 137 modules / 455 fns / 1058 params / 145 pvars / 196 MI / 29 evts / 79 stats / 0 guides → 220 KB. Build-twice consolidated.json hash is byte-identical across runs (determinism preserved).** New tests: 7 orchestrator-consolidated integration tests (canonical path + schema parse, non-zero stats, build-twice determinism, first-run baseline hint, dry-run no-write, JSON summary `indexBuilt`, validate-only `indexBuilt=false`); 716 total project tests passing.
- **M6 — Multi-version verification.** Empirically verified the dynamic-discovery design from ADR-009: build runs against all `data/{X.Y}/` directories without any code path enumerating versions. 3.5 and 3.6 build cleanly (149 + 210 generated files); 3.4 surfaces its known upstream JSON-parse defect cleanly via the validation pipeline (exit 3, file path + byte offset reported). Version isolation verified end-to-end: zero cross-references between 3.5 and 3.6 in any generated file (modules `.md`, core `.md`, guides `.md`, or `consolidated.json`). Build-twice across versions produces byte-identical output (deterministic). The verification rebuild matched the M5-committed working tree exactly — no commit needed for M6 since the design was already proven by M3-M5's commits.
- **M7 — Skill authoring.** Three hand-authored `SKILL.md` files plus per-version `ser-lineage-notes.md`, completing the plugin's runtime surface. `opensips-routing/SKILL.md` (302 lines, 7 required sections, 5 Bad/Good paired examples covering registrar/stateful proxy/NAT/auth/dispatcher confusion patterns) authors and edits OpenSIPs route scripts. `opensips-modules/SKILL.md` (348 lines including the generated catalog) routes Claude to the right per-module reference via a 194-row Module Index table generated by `scripts/build-module-index/` from the consolidated index — paired `<!-- MODULE_INDEX:BEGIN/END -->` markers make `npm run build:skills` byte-idempotent. `opensips-security-advisor/SKILL.md` (58-line scaffold) declares the trigger surface and integration contract; substantive review patterns are owned by a separate authoring agent per ADR-005. `ser-lineage-notes.md` for both 3.5 and 3.6 (144 lines each, 6 Bad/Good pairs each) document the cross-project guardrail with concrete sibling-confusion examples (PV access functions, module loading directives, route invocation conventions, registrar `save()` signature, dispatcher algorithm flags, accounting setup) — Bad examples labeled "sibling-project pattern" without naming any sibling per ADR-008. Sibling-name grep across all five hand-authored files: zero hits except the single allowed "SIP Express Router (SER)" lineage acknowledgment per file. 19 new tests for `build-module-index/` (catalog row construction, table rendering, paired-marker injection idempotency, end-to-end against real `data/3.6/`); 735 total project tests passing.
- **M9 — Test suite and CI.** Vitest configured with v8 coverage; npm scripts for `test`, `test:watch`, `test:coverage`, `test:golden`, `test:e2e` all wired. Golden-file regression tests (`tests/golden/`) cover three module renderings (tm, acc, sl), three core renderings (variables, operators, flags), and the consolidated index — fixtures and expected outputs committed under `tests/__fixtures__/golden/`; regenerate via `tsx tests/__fixtures__/golden/regenerate.ts` (workflow documented in test-strategy.md). End-to-end tests (`tests/e2e/`) exercise the orchestrator end-to-end across full-pipeline (5 cases including exit codes 0/2/3/5), version-isolation (4 cross-version cleanliness checks), and a permanent determinism test (build-twice byte-identical for both 3.5 and 3.6, ~8s runtime). Golden-path demos document (`docs/testing/golden-path-demos.md`, 719 lines, 16 demos) — the manual checklist maintainers run against Claude Code before each release; covers should-trigger, should-not-trigger, reference-loading verification, version-aware behavior, and multi-skill coordination cases. ### Notes
- **`.broken` marker convention added.** A version directory may now contain `data/{version}/.broken` to signal that the version's upstream data has a known defect; the build skips it with a clear warning and exits cleanly rather than failing. Per ADR-009, this is a DATA signal — adding or removing the marker is a data operation, no code change required. `data/3.4/.broken` is committed pointing at the upstream JSON-parse defect documented in the M1 notes; remove the marker once the upstream extraction is corrected.
- Real-data validation surfaced an upstream JSON-parse defect in `data/3.4/core/variables.json` at byte 80262 (line 1474, column 7 — stray `.0` token mid-object). Per CLAUDE.md Rule 3, the fix belongs upstream in `opensips-docs-collector`, not here. The pipeline correctly detected and reported it; 3.4 builds will continue to fail validation until the extraction is corrected upstream and `data/3.4/` re-mirrored. 3.5 and 3.6 validate clean.
- Security advisor skill ships as a scaffold; substantive review patterns are authored by a separate agent.
- Project requires Claude Code; not currently supported in Claude.ai web or the Claude API directly.

### Known notes for users
- When using `npm run build -- --json`, npm prepends a banner to stdout that breaks JSON consumers. Use `npm run --silent build -- --json` or invoke `npx tsx scripts/build-references.ts --json` directly. Documented because the JSON contract requires clean stdout.
