## `branch_route`

Request's branch routing block. It contains a set of actions to be taken for each branch of a SIP request. Processing: the SIP request (with the branch particularities, like RURI, branch flags).

- **Trigger:** preparation a new branch (of a request); the branch is well formed, but not yet sent out.
- **Can call routes:** yes

**Syntax:**

```
branch_route[1]
```

**Example.** Example of usage showing arming and using a branch route..

```opensips
route {
    lookup("location");
    t_on_branch("1");
    if(!t_relay()) {
        sl_send_reply(500, "Internal Server Error");
    }
}
branch_route[1] {
    if($ru=~"10\\.10\\.10\\.10") {
        # discard branches that go to 10.10.10.10
        drop();
    }
}
```

## `error_route`

The error route is executed automatically when a parsing error occurs during SIP request processing, or when a script assert fails. It allows the administrator to decide what to do in such error cases. Processing: failed request.

- **Trigger:** parsing error in "route"
- **Can call routes:** yes

**Available variables:** `$(err.class)`, `$(err.level)`, `$(err.info)`, `$(err.rcode)`, `$(err.rreason)`

**Syntax:**

```
error_route { ... }
```

**Example.** Example of usage showing error logging and replying..

```opensips
  error_route {
     xlog("--- error route class=$(err.class) level=$(err.level)
            info=$(err.info) rcode=$(err.rcode) rreason=$(err.rreason) ---\n");
     xlog("--- error from [$si:$sp]\n+++++\n$mb\n++++\n");
     sl_send_reply("$err.rcode", "$err.rreason");
     exit;
  }
```

## `event_route`

The event_route is used by the OpenSIPS Event Interface to execute script code when an event is triggered. The name of the route is the event that has to be handled by that route. The route itself is executed asynchronously with regards to the trigger moment. Processing: the event triggered.

- **Trigger:** the event_route module when an event raised by the OpenSIPS Event Interface
- **Can call routes:** no

**Syntax:**

```
event_route[E_PIKE_BLOCKED]
```

**Example.** Example of usage handling an E_PIKE_BLOCKED event..

```opensips
  event_route[E_PIKE_BLOCKED] {
    xlog("The E_PIKE_BLOCKED event was raised\n");
  }
```

## `failure_route`

Failed transaction routing block. It contains a set of actions to be taken each transaction that received only negative replies (>=300) for all branches. Processing: the original SIP request (that was sent out).

- **Trigger:** receiving or generation(internal) of a negative reply that completes the transaction (all branches are terminated with negative replies)
- **Can call routes:** yes

**Syntax:**

```
failure_route[1]
```

**Example.** Example of usage showing handling failed transactions..

```opensips
route {
    lookup("location");
    t_on_failure("1");
    if(!t_relay()) {
        sl_send_reply(500, "Internal Server Error");
    }
}
failure_route[1] {
    if(is_method("INVITE")) {
         # call failed - relay to voice mail
         t_relay("udp:voicemail.server.com:5060");
    }
}
```

## `local_route`

The local route is executed automatically when a new SIP request is generated by TM, internally (no UAC side). This is a route intended to be used for message inspection, accounting and for applying last changes on the message headers. Routing and signaling functions are not allowed. Processing: the new request.

- **Trigger:** TM generating a brand new request
- **Can call routes:** no

**Syntax:**

```
local_route { ... }
```

**Example.** Example of usage showing header manipulation and accounting..

```opensips
  local_route {
     if (is_method("INVITE") && $ru=~"@foreign.com") {
        append_hf("P-hint: foreign request\r\n");
        exit;
     }
     if (is_method("BYE") ) {
        acc_log_request("internally generated BYE");
     }
  }
```

## `onreply_route`

Reply routing block. It contains a set of actions to be taken for SIP replies. Processing: the received reply.

- **Trigger:** receiving of a reply from the network
- **Can call routes:** yes

**Syntax:**

```
onreply_route {...} or onreply_route[0] {...} or onreply_route[N] {...}
```

**Example.** Example of usage showing global, per transaction, and per branch reply routes..

```opensips
route {
        seturi("sip:bob@opensips.org");  # first branch
        append_branch("sip:alice@opensips.org"); # second branch

        t_on_reply("global"); # the "global" reply route
                              # is set the whole transaction
        t_on_branch("1");

        t_relay();
}

branch_route[1] {
        if ($rU=="alice")
                t_on_reply("alice"); # the "alice" reply route
                                      # is set only for second branch
}

onreply_route {
        xlog("OpenSIPS received a reply from $si\n");
}

onreply_route[alice] {
        xlog("received reply on the branch from alice\n");
}

onreply_route[global] {
        if (t_check_status("1[0-9][0-9]")) {
                setflag(1);
                log("provisional reply received\n");
                if (t_check_status("183"))
                        drop;
        }
}
```

## `route`

Request routing block. It contains a set of actions to be taken for SIP requests. Processing: the triggering SIP request.

- **Trigger:** receiving an external request from the network.
- **Can call routes:** yes

**Syntax:**

```
route{...} or route[0]{...}
```

**Example.** Example of usage showing main route and a secondary route call..

```opensips
route {
     if(is_method("OPTIONS")) {
        # send reply for each options request
        sl_send_reply(200, "OK");
        exit();
     }
     route(1);
}
route[1] {
     # forward according to uri
     forward();
}
```

## `startup_route`

The startup_route is executed only once when OpenSIPS is started and before the processing of SIP messages begins. This is useful if some initiation actions are needed, like loading some data in the cache, to ease up the future processing. Notice that this route, compared to the others is not triggered at the receipt of a message, so the functions that can be called here must not do processing on the message. Processing: Initializing functions.

- **Trigger:** At startup, before the listener processes are started.
- **Can call routes:** no

**Syntax:**

```
startup_route { ... }
```

**Example.** Example of usage showing database query and cache storage..

```opensips
  startup_route {
    avp_db_query("select gwlist where ruleid==1",$avp(i:100));
    cache_store("local", "rule1", "$avp(i:100)");
  }
```

## `timer_route`

The timer_route is a route executed periodically at a configured interval of time specified next to the name (in seconds). Similar to startup_route, this route does not process a SIP message. Multiple timer routes (possibly at differing running intervals) are allowed. Processing: Functions that do periodic, recurring processing.

- **Trigger:** The timer worker process.
- **Can call routes:** no

**Syntax:**

```
timer_route[name, interval]
```

**Example.** Example of usage showing periodic database update..

```opensips
  timer_route[gw_update, 300] {
    avp_db_query("select gwlist where ruleid==1",$avp(i:100));
    $shv(i:100) =$avp(i:100);
  }
```
